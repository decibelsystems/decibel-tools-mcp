# Decibel Tools 3.0 — What Changed Architecturally

**Published:** `@decibelsystems/tools@3.0.0`, 2026-09-06 (npm `latest`, up from 2.1.4)
**Scope:** the 3.0 arc is **38 commits over 10 days** (2026-08-28 → 2026-09-06),
PRs #49–#73, three epics — EPIC-0038 Runtime, EPIC-0037 Post Office, EPIC-0036 Zoom.
The npm jump 2.1.4 → 3.0.0 spans more history than that; the architecture below is
the 38.
**Written for:** Rich — architecture and reasoning, not a release note. The
line-by-line list is in [`CHANGELOG.md`](../../CHANGELOG.md).

---

## The one idea

Everything in 3.0 follows from a single sentence:

> Decibel Tools is not a daemon, an MCP server, a CLI, a store and a VS Code
> extension that happen to share a repo. It is **one runtime with several
> adapters.**

An adapter translates a transport and establishes project context. It does *not*
instantiate its own store, caches, project registry, or write path.

There's a test for any future code that falls out of this: **why is this in the
stdio server instead of the runtime?** If the answer isn't "because it is
specifically about stdio/MCP transport," it belongs elsewhere.

### Why it needed saying

The old topology wasn't a design, it was an accretion. Every MCP client that
connected started a *complete* Decibel — its own store implementation, its own
project resolver, its own cache, its own write path. Measured before the work
started: **seven stdio runtimes plus one daemon, ~883 MB RSS**, seven independent
opinions about the same files on disk.

That's not primarily a memory problem, and it's worth being precise about why,
because "we cut RAM" is the least interesting thing here. It's a *correctness*
problem:

- Seven writers to one directory, each allocating issue IDs by reading the
  directory and picking the next number. Four duplicate-ID groups on disk proved
  it wasn't theoretical.
- Two live `createIssue` implementations (`src/sentinelIssues.ts` and
  `src/tools/sentinel.ts`) emitting *different formats* into the same folder.
- Loading the `senken` facade meant seven `pg.Pool` instances against Mother's
  production Postgres.

One runtime means one lifecycle, one tool implementation, one project resolver,
one cache, one store, and one behavioural model across MCP, CLI and VS Code.

## The five structural moves

### 1. A lifecycle primitive, not startup logic copied per surface

`ensureRuntime({projectRoot, protocolVersion})` is now the single entry point
used by every caller — MCP, CLI, VS Code, shell hooks.

Two decisions inside it are worth calling out:

- **Arbitration is the socket bind or an atomic startup lock — never a PID
  file.** `~/.decibel/daemon.pid` had already gone stale once and pointed at
  nothing. A PID file answers "did something write this file," not "is a runtime
  listening."
- **Protocol negotiation happens at handshake, not per call.** A version-skewed
  runtime is refused once, up front, rather than producing puzzling failures
  scattered across later calls.

### 2. Layers that don't know about each other

Split into named, separable pieces: `IssueRepository` / `IssueCodec` /
`ProjectResolver` / `RuntimeService` / `RuntimeClient` / `DaemonController`.

The property being bought: **transport doesn't know storage, storage doesn't
know MCP, and project detection stops happening implicitly.** No caller knows
whether an issue is on disk as markdown, YAML, or eventually SQLite.

### 3. Adapters are clients — and never quietly become writers

The thin stdio client (`src/transports/thinStdio.ts`) connects to the shared
runtime instead of being one.

The important constraint is a negative one: **there is no in-process fallback
for mutations.** A thin client auto-starts the runtime, retries briefly, then
fails with an actionable error. The tempting alternative — "if the runtime isn't
reachable, just do the write locally" — defeats the entire invariant. A proxy
that silently becomes a writer under load is exactly the seven-writers problem
coming back on the worst possible day.

### 4. Private facades left the public package

`senken` (live trading Postgres), `deck`, `mother` and `terminal` used to ship as
compiled JavaScript inside the public npm tarball — a public description of a
private trading system and a wallet-spending tool that the package could never
actually reach.

They are now **extensions**, loaded at boot from `extensions.allow` in
`~/.decibel/config.yaml`, **by absolute path only**. Two deliberate constraints:

- A bare specifier would resolve against `node_modules`, which would hand facade
  selection to anyone who can write a package. Absolute paths only.
- An extension may not shadow a registered facade name.

`DECIBEL_APPS=1` is gone and **no environment variable replaces it.** The
reasoning generalises: config-file state that the owner edits beats environment
state that a generator has to remember. A regenerated launchd plist had silently
dropped those four facades once — and `/health` cheerfully reported `status: ok`
with no hint that four were missing.

### 5. Faults are contained per facade

Two mechanisms:

- **Error isolation.** No facade fault escapes `dispatch()` — including throws
  from parameter coercion and facade resolution (which the transports would
  otherwise convert into an MCP *protocol* fault rather than a failed tool call),
  and including dispatch event listeners, which run synchronously on the call
  path.
- **A per-facade circuit breaker** whose signal is *unresponsiveness*, not
  unhappiness. A throw always counts; an error slower than 2s counts; a *fast*
  error leaves the counters untouched — because a tool that correctly and quickly
  says "no" is healthy. Five consecutive faults open a facade for 30s, then
  exactly one probe at a time, so a recovering database gets one connection
  attempt rather than six simultaneous ones.

## The intellectual heart: absence has to be loud

If there's one idea in 3.0 worth carrying to other projects, it's this one.

The observation that reframed the whole release:

> **Every failure this project has actually shipped returned `ok: true`.**

Three real incidents, same shape:

| What happened | What it reported |
|---|---|
| Voice inbox dead for 5.5 hours | `voice 0` |
| Regenerated plist dropped 4 facades | `/health: status ok` |
| `/batch` called a facade that doesn't exist | `{ok: true}` |

None of these were crashes. Every one was a *successful-looking* answer that
happened to be empty. The cause was the same two lines of defensive code
repeated across the codebase — `if (!parsed) continue` and `catch {}` — each of
which turns "I couldn't read this" into "there was nothing here."

**What changed:** thirty-one store-backed reads can now tell four situations
apart — an **empty** store, an **unreadable** one, an **unparseable** one, and a
**project that doesn't resolve**. Reads that skip a record carry `store_status`
and `unreadable_count`. Three paths now fail loudly instead, because a partial
answer would have been actively dishonest: `context`'s whole-file `facts.json`
and `events.json`, and `auditPolicies` — where a single malformed policy used to
abort the audit and then report `summary.fail: 0`.

Correspondingly: **an unregistered facade is now a hard error, not an empty
success.** Failing closed is only safe if the failure is audible.

This principle keeps paying out. It's still finding bugs a week later — the
session-init hook was rendering `voice 0` identically whether the inbox was
empty, the call errored, or the facade didn't exist. Same silent zero, in the
tooling written *because of* the original incident.

## Store integrity

The store had accumulated real damage, and it got repaired once and then fenced.

- **One writer.** `sentinelIssues.createIssue` now delegates to
  `FsIssueRepository`. The second implementation is gone.
- **ID allocation is serialized across processes.** The subtlety that matters:
  the lock spans allocation *through successful write*. Serializing only the ID
  scan leaves the race fully intact, because both processes still compute the
  same number before either file lands. The write itself is `O_EXCL` as a second,
  independent defence against callers that never take the lock at all.
- **Structured fields are parsed, mutated, serialized and atomically renamed** —
  never edited by regex. Values containing `#`, `:`, `---` or a markdown heading
  now survive read-back.
- **Repaired, once:** `degraded` 10 → 0, duplicate IDs 4 groups → 0, wrong
  `project` values 18 → 0. All three are now invariants CI can fail on.

Two findings from this work are worth Rich's attention because they're general:

**Most "corrupt" records weren't corrupt.** Of the 10 degraded issues, most
carried a completed resolution and were open only because an old status write had
failed. The correct repair was to *close* them, not reformat them. Reaching for
the migration script would have preserved the wrong thing carefully.

**Status was stored twice by hand.** Markdown records mirror status into the
body; 16 had drifted from frontmatter — reading `open` to a human while every
tool correctly reported them closed. `close_issue` rewrote the mirror,
`updateIssue` never did. No test caught it, because every test asserted through
frontmatter, which was never wrong. A duplicated field with one lazy writer is
invisible to tests that only read the diligent one.

## The release gate: the tool torture test

3.0 is the first release blocked on a gate rather than on judgement. Eight
generated sweeps run the entire surface across all four transports.

| Sweep | What it gates |
|---|---|
| **S0** enumeration | no unclaimed actions, no dangling actions, no expired waivers |
| **S1** envelope | every action answers in a well-formed envelope |
| **S2** absence | every read distinguishes the four situations above |
| **S3** round-trip | hostile values survive write → read |
| **S4** transports | stdio, thin, http-call, http-batch agree; differences declared |
| **S5** concurrency | 50 concurrent creates across 10 processes; crash mid-write |
| **S6** tier/extension | the apps boundary holds, and no env var reopens it |
| **S7** artifact | the packed tarball, not the repo |

Three design choices make it more than a big test suite:

**The surface is generated from the kernel's own registries, never enumerated by
hand.** Adding a tool without giving it coverage turns the build red. A
hand-maintained list of what to test rots into a list of what someone remembered.

**Every action is either claimed by a sweep or waived by name** in
`waivers.yaml`, with a reason, an owner, and an **expiry**. Waivers expire, and
an expired waiver fails the build. A waiver is a visible, reviewable decision; an
untested tool is not.

**Every sweep carries a calibration probe** asserting it can see a deliberately
broken tool *before* it's believed about the healthy ones. This was not
precaution — it was earned:

- Six of eighteen S2 findings were **the harness lying**: fixtures planted at
  paths no reader actually globs, so tools that handled absence correctly were
  reported broken.
- S5's first crash test reported four successful `SIGKILL`s while all four
  victims were still running.

A green sweep is worth exactly as much as your evidence that it can go red.

**881 tests at release.** (894 as of this writing.)

## Also new in 3.0

- **guardian** (core) — dependency, secret, HTTP and config scanning with A–F
  grading. Wired into a pre-push hook that blocks on D/F findings.
- **postoffice** (EPIC-0037) — model-agnostic agent-to-agent messaging, all seven
  verbs, two-way threaded exchange verified live.
- **conductor** — run / dryrun / trace / cost / egress / routing.
- **zoom** (EPIC-0036) — meeting-summary ingestion. **Ships dark**, gated behind
  `DECIBEL_ZOOM=1`, and **not yet run against a live Zoom account.**

**Surface:** 26 core facades / 183 actions, +5 pro facades / 224 actions total
under a runtime license check, plus apps-tier facades that are no longer in the
package at all.

## Deliberately unfinished

Stated plainly, because a release note that implies completeness is its own kind
of silent zero:

- **EPIC-0038 Phase 6 (backlog hygiene)** is open by choice. ~10 issues need
  Ben's judgement; the call was not to block 3.0 on triage. The epic remains
  `in_progress`.
- **Filename convergence was dropped on purpose** (ADR-0010). 79 timestamp-slug
  filenames stay: 49 provenance events and 2 ADRs reference them, and provenance
  events are immutable audit records. Identity is the `id:` field, which is
  already how records resolve. Renaming files to look tidy would have broken real
  references to make a directory listing prettier.
- **`zoom` has never talked to a live Zoom account.**
- **Two builds still share one `dist/`** (ISS-0159). `postpack` restores the dev
  build after packing, and a test pins that behaviour — but the structural fix
  (one build plus `files` negation) was deliberately not attempted hours after a
  major release.

## The through-line

If Rich reads one paragraph:

3.0 replaced *N* half-systems with one runtime and a set of adapters, then spent
most of its effort on a single class of bug — **code that reports success when it
has failed.** The architecture work (one writer, one resolver, one lifecycle,
contained faults) removes the conditions that produce silent zeros. The torture
test is the standing proof that they stay removed, and it is trusted only insofar
as it has been shown to go red on a tool known to be broken.
